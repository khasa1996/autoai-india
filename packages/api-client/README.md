# Shared API client

`createApiClient({ baseUrl, fetch? })` works in browsers and native JavaScript runtimes without reading platform environment variables. Authentication uses session cookies exclusively; bearer tokens are not supported by this API. Native runtimes must provide a fetch implementation with a persistent cookie jar for authenticated requests; this client does not implement native session storage. Remote endpoints require HTTPS and redirects are rejected. `catalogue()` validates the response at runtime; generic `request<T>` accepts a Zod schema for runtime validation. Other convenience methods expose typed contracts only.

`recommendFromApiVehicles(rows, needs, policy?)` maps verified API catalogue rows into domain recommendations. It never invents seat counts, transmission, features, option compatibility or reviewer provenance. Required scalar specification keys are `seats` (number), `transmission` (`manual` / `automatic`), `sourceType` (`manufacturer` / `dealer` / `regulator`), `retrievedAt` (ISO datetime), and `verifiedBy` (reviewer identifier). `features` and `compatibleOptionIds` are JSON-encoded string arrays because the API currently accepts flat scalar specification maps. Explicit `[]` is supported; absent values are excluded with reasons. API records must come from the authorized reviewed catalogue endpoint. A client-side provenance object does not authenticate its author.

A default 90-day verification window applies and is returned with results; stricter policies may be supplied. `excludedCount` and `exclusions` disclose invalid, incomplete, stale and unsuitable rows. These are deterministic vehicle matches, not AI-generated vehicle facts.

`requestBooking(offerId, idempotencyKey)` requires a caller-generated stable key of 8–128 ASCII letters, digits, underscores or hyphens. Generate one key per booking intent and persist/reuse it unchanged across network retries. A new intended booking must use a new key; the client deliberately does not generate one per request.
